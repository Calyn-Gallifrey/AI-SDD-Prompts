# UAW `.project-ai` 規範索引

## 1. 目的

本索引用於 UAW 專案中 `.project-ai` 目錄的檢索與裝配，供人與 AI 在以下環節使用：

- 生成功能級 `spec`
- 生成設計文檔 `design`
- 生成任務編排 `tasks`
- Builder / AI 實施代碼
- 增強需求時回看既有規範與歷史功能資產

本索引不是功能需求，不直接描述某個功能要做什麼；它只回答：

1. 這次任務屬於什麼場景
2. 這次任務應讀哪些規範 / 上下文 / 模板
3. 這些規範在 `spec / design / tasks` 哪個環節被使用

補充：

- `.project-design-docs/` 用於存放迭代設計文檔，可作為 `design` 環節的外部參考資料。
- 功能級資產建議按功能存放，例如：

```text
.project-features
└── sprint5
    └── agreement-info-query
        ├── spec.md
        ├── tasks.md
        └── archive.md
```

若保留 `.project-design-docs` 作為獨立設計庫，則功能級 `design` 可放在：

```text
.project-design-docs/sprint5/agreement-info-query-design.md
```

## 3. 主分類說明

### 3.1 context（上下文）

此目錄只存放：

- 領域字典
- 項目特殊背景
- 兼容性說明
- 索引本身

不存放代碼規則，不存放模板，不存放任務編排。

#### 目前文件

- `transactions字典清单.md`
  - 用途：交易類型、命名、模組歸屬、package 命名等背景上下文
- `新增transaction如何兼容caseTrakcer功能.md`
  - 用途：transaction 增量開發時的專案特殊兼容背景
- `index.md`
  - 用途：how-to / rules / templates 的檢索路由文件

---

- 外部接口應怎麼封裝

- DB / ORM 代碼應怎麼寫

#### 目前文件

## 4. 按環節的檢索路由

> 原則：按項目階段分類僅作為檢索視角，不作為主目錄結構。

### 4.1 `spec` 環節先讀什麼

當目標是生成功能提案 / 增量規格時，優先讀：

- `context/transactions字典清单.md`
- `context/新增transaction如何兼容caseTrakcer功能.md`（若涉及 transaction 類型或 caseTracker）
- `rules/2.如何新增一个transaction业务功能包结构.md`
- `rules/1.如何新增一个数据库表.md`（若涉及表結構變更）
- `rules/6.如何调用epi网关接口.md`（若涉及 EPI）
- `rules/9.如何开发om api防腐代码.md`（若涉及 OM）
- `templates/spec-template.md`

`spec` 環節的核心任務不是寫代碼，而是回答：

- 這次功能屬於哪個模組
- 它建立在哪些存量之上
- 本次是增量、修改還是重構
- 哪些規則後續設計一定會用到
- 哪些風險與兼容點要提前寫進規格

---

### 4.2 `design` 環節先讀什麼

當目標是生成設計文檔時，優先讀：

- `rules/3.如何开发一个后端API接口代码.md`
- `rules/4.如何开发mybatis的ORM代码.md`
- `rules/5.如何获取当前用户.md`
- `rules/7.如何基于mapstruct进行值对象转换.md`
- `rules/model/8.1-BO对象生成规范.md`
- `rules/model/8.2-VO对象生成规范.md`
- `rules/model/8.3-DTO对象生成规范.md`
- `rules/model/8.4-Entity对象生成规范.md`
- `rules/6.如何调用epi网关接口.md`（若涉及 EPI）
- `rules/9.如何开发om api防腐代码.md`（若涉及 OM）
- `.project-design-docs` 中相近功能的設計文檔（若存在）
- `templates/design-template.md`

`design` 環節的核心任務是回答：

- 包與類如何落位
- 需要哪些 BO / DTO / VO / Entity
- service / controller / mapper / converter 如何分工
- 外部接口如何封裝
- 當前用戶與轉換邏輯如何落位
- 哪些規則在 tasks 階段必須變成顯式執行步驟

## 6. 使用原則

1. `context` 不寫代碼規則，只提供背景與兼容信息。
2. `rules` 只放真正決定工程結構、代碼寫法、測試寫法的規則。
3. `templates` 只放固定輸出骨架。
4. `spec` 先從 `context + rules + spec-template` 出發。
5. `design` 先從 `rules + 既有設計文檔 + design-template` 出發。
6. `tasks` 先從 `rules + testing + tasks-template` 出發。
7. 每次任務完成後，如果新增了新的通用規則，應回寫 `.project-ai/rules` 或 `.project-ai/context`，並同步更新本索引。
8. `.project-design-docs` 可以保留，但它是設計參考庫，不取代功能級 spec / tasks。
