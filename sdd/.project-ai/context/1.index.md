# UAW AI 知识路由索引（index）

> 本文件是 UAW 项目的**知识路由索引 / 装配调度入口**。  
> 本文件不是功能 spec，不是 design，不是 tasks，也不是任务本身。  
> 本文件只负责：**识别任务 → 装配知识 → 路由模板 → 指导下一阶段输入**。

---

## 1. 角色说明

### 1.1 `.project-ai/context`
用于存放**上下文基线**，包括但不限于：
- 领域字典
- 项目特殊约束
- 兼容性背景
- 既定业务术语
- 需要跨功能复用的解释性知识

这些内容用于帮助 AI 和开发理解“项目是什么、模块是什么、已有边界是什么”。

### 1.2 `.project-ai/rules`
用于存放**工程规则基线**，包括但不限于：
- 包结构规则
- API 编写规则
- ORM / XML 规则
- BO / DTO / VO / Entity 生成规则
- current user 处理规则
- mapstruct 转换规则
- 测试规则
- 对外集成规则

这些内容用于约束“代码应该怎么写、文件应该怎么落位、测试应该怎么补”。

### 1.3 `.project-ai/templates`
用于存放**装配与产出模板**，包括但不限于：
- `proposal-input-template.md`
- `spec-template.md`
- `design-template.md`
- `tasks-template.md`
- `archive-template.md`

这些内容用于保证每次功能资产输出结构一致、可承接、可归档、可复用。

## 2. UAW AI 工程链条

UAW 当前采用如下链条：

`proposal-input-template.md`
→ `index.md` 识别任务并装配知识
→ 生成 `spec.md`
→ 生成 `design.md`
→ 生成 `tasks.md`
→ AI / Builder 实施代码
→ 人工审核
→ 生成 `archive.md`
→ 下一次 enhancement / refactor 再次引用 `archive.md + spec.md + design.md + 当前 Git 代码`

说明：
- **当前 Git 代码**是实物基线
- **历史功能资产（archive/spec/design/tasks）**是知识基线
- 二者冲突时，默认以当前 Git 代码为准，并在新一轮 spec 中明确标注差异

## 3. 任务识别维度

每次任务进入系统时，至少应识别以下维度：

### 3.1 功能类型
- query
- submit
- edit
- enhancement
- refactor
- fix

### 3.2 所属模块
- transaction
- agreement
- myDocument
- policy
- 其他业务模块

### 3.3 技术面
- API
- ORM
- mapstruct
- current user
- test
- OM
- EPI
- DB script
- converter / helper / enum

### 3.4 变更范围
- 新增字段
- 新增查询条件
- 新增 transaction type
- 新增接口
- 修改接口
- 引入外部依赖
- 扩展返回对象
- 增强既有流程
- 局部重构

### 3.5 禁止变更
- 不改表
- 不改 path
- 不改 helper
- 不改既有核心流程
- 不改既有对外接口契约

### 3.6 任务形态
- 新功能
- enhancement（既有功能增强）
- refactor（既有功能重构）
- fix（问题修复）

## 4. Base Context 与 Conditional Context 装配逻辑

### 4.1 Base Context（基础上下文）
每次任务默认优先装配以下内容：
- 项目既定目录结构
- 当前模块命名与包结构基础规则
- `.project-ai/rules` 中的核心工程规则
- 当前功能对应 sprint 下的既有功能资产（若存在）
- 当前 Git 代码扫描范围内的存量代码

Base Context 的目标是保证：
- AI 不脱离项目语境
- AI 不脱离当前代码现状
- AI 不凭空生成与项目风格冲突的内容

### 4.2 Conditional Context（条件上下文）
根据任务识别维度按需装配：
- 如果模块 = transaction → 装配 transaction 相关上下文与规则
- 如果技术面包含 ORM → 装配 ORM / Entity / XML 规则
- 如果技术面包含 API → 装配 API / BO / DTO / VO 规则
- 如果技术面包含 mapstruct → 装配 mapstruct 规则
- 如果技术面包含 current user → 装配 current user 规则
- 如果技术面包含 test → 装配 testing 规则
- 如果涉及 OM / EPI → 装配对应集成规则
- 如果是 enhancement / refactor → 装配历史功能资产（archive/spec/design/tasks）

Conditional Context 的目标是保证：
- 任务只加载必要知识
- 装配是有条件、有边界的
- 不把所有规则一次性塞给 AI

---

## 5. Rules 装配逻辑

### 5.1 默认装配
满足以下任一情况时，优先装配对应规则：
- 涉及新增包 / 类 / 模块落位 → 包结构规则
- 涉及接口 → API 规则
- 涉及数据库查询 / XML → ORM 规则
- 涉及对象生成 → BO / DTO / VO / Entity 规则
- 涉及上下文用户信息 → current user 规则
- 涉及对象转换 → mapstruct 规则
- 涉及测试 → testing 规则
- 涉及外部依赖 → OM / EPI 规则

### 5.2 Enhancement / Refactor 特殊规则
若任务类型为 enhancement / refactor，则除上述规则外，还应优先装配：
- 历史功能 archive 中记录的关键决策
- 原 spec 中的边界与 non-goals
- 原 design 中的关键分层与落位
- 原 tasks 中的顺序与检查项（按需）
- 当前 Git 代码扫描结果

spec 经确认后，生成：
- `.project-ai/templates/design-template.md`

design 经确认后，生成：
- `.project-ai/templates/tasks-template.md`

### 6.5 归档阶段
实现完成且审核通过后，生成：
- `.project-ai/templates/archive-template.md`

## 7. spec / design / tasks 三阶段优先装配内容

### 7.1 spec 阶段优先装配
目标：定义本次功能目标、边界、双基线与验收标准

优先装配：
- proposal 输入摘要
- Base Context
- 任务类型对应的 Conditional Context
- 当前 Git 代码扫描结果
- 历史功能资产（若为 enhancement / refactor）
- spec-template

spec 阶段重点回答：
- 本次做什么
- 建立在什么存量之上
- 哪些地方不能改
- 哪些规则后续必须沿用
- design 必须承接哪些约束

### 7.2 design 阶段优先装配
目标：回答“如何实现”

优先装配：
- 已确认的 spec
- 既有设计文档（`.project-design-docs/...`）
- 当前 Git 代码现状
- 对应工程规则
- design-template

design 阶段重点回答：
- 包与类如何落位
- 模块如何拆分
- 数据如何流转
- 外部依赖如何调用
- tasks 必须遵守哪些执行约束

### 7.3 tasks 阶段优先装配
目标：形成 Builder / AI 可施工的阶段化任务

优先装配：
- 已确认的 spec
- 已确认的 design
- 当前 Git 代码现状
- 规则装配摘要
- testing 规则
- tasks-template

tasks 阶段重点回答：
- 先做什么，后做什么
- 每个阶段输出什么
- 哪些依赖必须先满足
- 交付前如何自检
- 归档前置条件是什么

## 8. 与 `proposal-input-template.md` 的衔接方式

### 8.1 proposal 是唯一正式入口
每次功能任务必须从 `proposal-input-template.md` 启动。  
proposal 至少提供：
- 业务任务信息
- AI 知识底座路径
- 现状扫描范围
- 设计文档选择规则
- 历史功能资产引用（仅 enhancement / refactor）
- 输出位置
- 归档要求

### 8.2 index 的职责
收到 proposal 后，index 负责：
1. 解析任务识别维度
2. 装配 base context
3. 装配 conditional context
4. 装配 rules
5. 选择 templates
6. 指导 spec / design / tasks 的生成顺序

---

## 9. 与 `archive-template.md` 的衔接方式

### 9.1 tasks 实施与审核完成后
由 AI / Builder 根据 `archive-template.md` 生成 `archive.md`

### 9.2 archive 的职责
archive 不是流水账，不是聊天记录，不是空壳总结。  
archive 的职责是：
- 固化本次最终方案
- 记录关键决策与取舍
- 明确当前仍有效的边界
- 给下一次 enhancement / refactor 提供推荐阅读顺序

### 9.3 index 在归档后的作用
index 不直接替代 archive。  
归档后：
- archive 成为下一轮功能引用入口
- index 仍然负责下一轮任务的知识装配与模板路由

---

## 10. Enhancement / Refactor 场景下的历史功能资产引用规则

若任务类型为 enhancement / refactor，必须执行以下引用顺序：

1. 先读上一轮 `archive.md`
2. 再读上一轮 `spec.md`
3. 再读上一轮 `design.md`
4. 再扫描当前 Git 代码现状
5. 如需复用施工顺序，再读上一轮 `tasks.md`

说明：
- archive 负责提供“最小必要历史结论”
- spec 负责提供原始目标、边界与验收标准
- design 负责提供实现方式与落位
- tasks 仅在需要复用顺序 / 检查清单时使用
- Git 代码始终是实物基线

---

## 11. 使用原则

1. index 只做路由，不代替功能文档
2. spec 不写 how-to，不写施工步骤
3. design 不复述 spec，不写流水账
4. tasks 不写需求说明，只负责施工编排
5. archive 不记录废弃方案作为最终结论
6. enhancement / refactor 必须显式引用历史资产
7. 若历史资产与 Git 代码冲突，以 Git 代码为准
8. 若任务形成通用增量，需回写 rules / templates / index

---

## 12. 最终目标

本索引服务的不是“生成几个 Markdown 文件”，而是支撑 UAW 项目的完整链路：

`proposal → index 装配 → spec → design → tasks → implementation → review → archive → 下一轮 enhancement / refactor`

只有这条链路跑通，UAW 的 AI 工程骨架才算真正落地。
