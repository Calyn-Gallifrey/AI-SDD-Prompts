# UAW AI 知识路由索引（index）

> 本文件是 UAW 项目的知识路由索引 / 装配调度入口。  
> 本文件不是 proposal，不是 spec，不是 design，不是 tasks，也不是 archive。  
> 本文件只负责：识别任务 → 装配知识 → 路由模板 → 约束阶段输出 → 保证链路闭环。

---

# 1. 文件定位

本文件服务于以下完整链路：

`proposal-input-template.md`
→ `index.md` 识别任务并装配知识
→ `spec.md`
→ `design.md`
→ `tasks.md`
→ implementation
→ review
→ `archive.md`
→ 下一轮 enhancement / refactor 再次引用历史资产

说明：

- 当前 Git 代码是**实物基线**
- 历史功能资产（archive / spec / design / tasks）是**知识基线**
- 二者冲突时，以当前 Git 代码为准，并在新一轮 spec 中明确标注差异

# 2. 目录角色说明

## 2.1 `.project-ai/context`
用于存放项目上下文基线，例如：

- 业务术语词典
- 模块边界说明
- 历史架构背景
- 兼容性说明
- 长期约束

## 2.2 `.project-ai/rules`
用于存放工程规则基线，例如：

- 包结构规则
- API 规则
- 数据访问规则
- 对象建模规则
- 转换映射规则
- 测试规则
- 集成规则
- 日志 / 异常规则
- 安全 / 审计规则

## 2.3 `.project-ai/templates`
用于存放模板：

- `proposal-input-template.md`
- `spec-template.md`
- `design-template.md`
- `tasks-template.md`
- `archive-template.md`

## 2.4 `.project-features/`
用于存放每次任务资产：

- `proposal-input.md`（如有）
- `spec.md`
- `design.md`
- `tasks.md`
- `archive.md`

## 2.5 `.project-design-docs/`
用于存放历史设计文档，仅作为辅助输入，不替代功能级 spec / design / tasks。

# 3. proposal 驱动字段映射

收到 `proposal-input-template.md` 后，index 必须优先解析以下字段：

## 3.1 必填字段

- 功能名称
- 功能类型
- 所属模块
- 一句话目标
- 变更范围
- 禁止变更
- 优先级

## 3.2 条件字段

- 历史功能目录（仅 enhancement / refactor）
- sprint
- 输出目录
- 指定参考设计文档
- 风险提醒

## 3.3 proposal 字段与后续阶段映射

| proposal 字段 | index 用途 | 下游阶段 |
|---|---|---|
| 功能名称 | 确定功能资产目录、识别相关设计文档 | spec / design / tasks / archive |
| 功能类型 | 路由流程模式、识别历史资产引用规则 | spec / tasks / archive |
| 所属模块 | 约束扫描范围、装配模块上下文与规则 | spec / design / tasks |
| 一句话目标 | 形成 spec 的目标起点 | spec |
| 变更范围 | 命中 rules、决定 design 与 tasks 施工层次 | spec / design / tasks |
| 禁止变更 | 形成 spec 边界、约束 design / tasks | spec / design / tasks |
| 优先级 | 决定标准模式 / Fast Lane 倾向、影响响应节奏 | spec / tasks |
| 历史功能目录 | 装配 enhancement / refactor 历史资产 | spec / archive |
| 指定参考设计文档 | 直接指定 design 参考输入 | design |
| 输出目录 | 固定功能资产落位 | spec / design / tasks / archive |
| 风险提醒 | 辅助判断风险等级与审核强度 | spec / tasks |

# 4. 任务识别维度

index 识别任务时，至少要判断以下维度：

## 4.1 功能类型
- query
- submit
- edit
- enhancement
- refactor
- fix

## 4.2 所属模块
- 任意业务模块（如 transaction / agreement / policy / servicing 等）

## 4.3 技术能力面
按 proposal 的“变更范围”与代码扫描结果综合判断，可能命中：

- 契约与接口（Contract & Interface）
- 持久化与查询（Persistence & Query）
- 对象模型与边界（Object Model & Boundary）
- 转换与映射（Transformation & Mapping）
- 身份 / 权限 / 审计（Identity / Auth / Audit）
- 外部依赖与防腐层（External Dependency & ACL）
- 校验 / 异常 / 错误语义（Validation & Error Semantics）
- 可观测性 / 日志 / 排障（Observability & Operability）
- 测试与质量门禁（Testing & Quality Gates）
- 兼容 / 迁移 / 演进（Compatibility / Migration / Evolution）
- 配置 / 路由 / 脚本（如适用）

## 4.4 风险等级
若 proposal 未填写风险等级，由 AI 结合 proposal、当前代码现状与设计文档背景自动判断，并写入 spec。

### low
- 单点小改
- 无外部依赖
- 无核心流程影响
- 易验证、易回滚

### medium
- 多层改动（API + Service + DB / Mapper）
- 有存量逻辑耦合
- 需要认真回归

### high
- 核心链路改动
- 外部系统强依赖
- 数据变更 / 高兼容风险
- 回滚成本高

# 5. Base Context 与 Conditional Context 装配逻辑

## 5.1 Base Context（基础上下文）
每次任务默认装配：

- 项目目录结构
- 当前模块基础语境
- 当前代码扫描范围
- 通用工程规范

Base Context 的目标：

- AI 不脱离项目语境
- AI 不脱离当前代码现状
- AI 不凭空生成与项目风格冲突的内容

## 5.2 Conditional Context（条件上下文）
按任务命中条件装配：

### 命中 enhancement / refactor
装配：

- 历史功能 archive
- 原 spec
- 原 design
- 原 tasks（按需）
- 当前 Git 代码现状

### 命中外部依赖
装配：

- 外部系统集成背景
- ACL / 网关规则
- 超时 / 重试 / fallback 规则

### 命中兼容性改动
装配：

- 兼容性上下文
- 既有边界说明
- 旧行为与新行为差异背景

### 命中特殊术语 / 特殊领域
装配：

- 领域字典
- 模块边界解释
- 业务映射说明

原则：

- 只装必要内容
- 禁止全量灌输
- 避免上下文污染

# 6. Rules 装配逻辑

按任务特征装配：

| 命中场景 | 装配规则 |
|---|---|
| 新增包 / 类 / 模块落位 | 包结构规则 |
| 接口变更 | API 规则 |
| 查询 / 存储 / XML | DB / Mapper 规则 |
| 新对象 / 字段模型 | Model 规则 |
| 对象转换 | Mapping 规则 |
| 外部系统接入 | Integration / ACL 规则 |
| 权限 / 审计 / current user | Security / Audit 规则 |
| 单测 / 集成测试 | Testing 规则 |
| 错误处理 / 日志 | Logging / Exception 规则 |

说明：

- Rules 装配必须服务于 spec / design / tasks
- 不允许把 rules 全量塞给 AI，再让 AI 自己猜重点

# 7. 模式选择逻辑

## 7.1 标准模式（Standard）
默认走标准模式，适用于：

- 新功能
- 多层改动
- 外部依赖
- 高风险需求
- 需要完整沉淀的 enhancement / refactor

使用模板：

- `proposal-input-template.md`
- `spec-template.md`
- `design-template.md`
- `tasks-template.md`
- `archive-template.md`

## 7.2 Fast Lane（小需求模式）
仅在满足以下条件时可走 Fast Lane：

- 单点小改动
- 无复杂设计变化
- 无高风险依赖
- 可快速验证

Fast Lane 使用：

- `proposal-input-template.md`
- mini-spec
- 精简 design（如适用）
- `tasks-template.md`
- archive-lite

说明：

- 是否走 Fast Lane，不由开发随意决定
- 必须由 index 根据 proposal + 当前代码现状 + 风险判断来决定
- 若走 Fast Lane，spec 中必须明确标注原因

# 8. 阶段装配重点

## 8.1 spec 阶段
目标：定义本次功能目标、边界、双基线与验收标准

优先装配：

- proposal 输入摘要
- Base Context
- Conditional Context
- 当前 Git 代码扫描结果
- 历史功能资产（若为 enhancement / refactor）
- `spec-template.md`

spec 阶段必须回答：

- 本次做什么
- 建立在什么存量之上
- 哪些地方不能改
- 哪些规则后续必须沿用
- design 必须承接哪些约束
- 风险等级是什么（若 proposal 未给出则由 AI 判断）

## 8.2 design 阶段
目标：回答“如何实现”

优先装配：

- 已确认的 spec
- 既有设计文档（`.project-design-docs/...`）
- 当前 Git 代码现状
- 对应工程规则
- `design-template.md`

design 阶段必须回答：

- 包与类如何落位
- 模块如何拆分
- 数据如何流转
- 外部依赖如何调用
- 异常 / 上下文 / 测试 / 性能如何处理
- tasks 必须遵守哪些执行约束

## 8.3 tasks 阶段
目标：形成 Builder / AI 可施工的阶段化任务

优先装配：

- 已确认的 spec
- 已确认的 design
- 当前 Git 代码现状
- 规则装配摘要
- testing 规则
- `tasks-template.md`

tasks 阶段必须回答：

- 先做什么，后做什么
- 每个阶段输出什么
- 哪些依赖必须先满足
- 如何自检
- 如何交付审核
- 归档前置条件是什么

# 9. 与 proposal-input-template 的衔接方式

## 9.1 proposal 是唯一正式入口
每次功能任务必须从 `proposal-input-template.md` 启动。

## 9.2 index 在 proposal 之后必须做的动作

1. 解析任务识别维度
2. 判定执行模式（standard / fast-lane）
3. 装配 Base Context
4. 装配 Conditional Context
5. 装配 Rules
6. 确定 spec / design / tasks / archive 的模板路由
7. 指导功能资产输出目录

## 9.3 proposal 与 index 的边界

- proposal 负责“告诉系统这次要干什么”
- index 负责“判断该读什么、按什么顺序读、接下来用什么模板”

proposal 不做路由，index 不代替 proposal。

---

# 10. 与 archive-template 的衔接方式

## 10.1 归档触发时机
tasks 实施完成并通过审核后，由 AI / Builder 基于 `archive-template.md` 生成 `archive.md`

## 10.2 archive 的职责
archive 不是流水账，不是聊天记录，不是空壳总结。  
archive 的职责是：

- 固化本次最终方案
- 记录关键决策与取舍
- 明确当前仍有效的边界
- 记录偏差、风险、遗留项
- 给下一次 enhancement / refactor 提供推荐阅读顺序

## 10.3 index 在归档后的作用
归档后：

- archive 成为下一轮功能引用入口
- index 负责下一轮任务的知识装配与模板路由
- 若本次形成通用增量，index 需支持回写后的新规则继续生效

# 11. Enhancement / Refactor 历史资产引用规则

若任务类型为 enhancement / refactor，必须执行以下顺序：

1. 先读上一轮 `archive.md`
2. 再读上一轮 `spec.md`
3. 再读上一轮 `design.md`
4. 再扫描当前 Git 代码现状
5. 如需复用施工顺序，再读上一轮 `tasks.md`

说明：

- archive 提供最小必要历史结论
- spec 提供原始目标、边界与验收标准
- design 提供实现方式与落位
- tasks 仅在需要复用顺序 / 检查清单时使用
- Git 代码始终是实物基线

# 12. 回写机制

当任务形成通用增量时，需回写：

## 12.1 rules
例如：

- 新包结构规范
- 新测试规范
- 新集成规范
- 新日志 / 异常规范

## 12.2 context
例如：

- 新术语
- 新模块边界
- 新兼容性背景

## 12.3 templates
例如：

- 模板字段优化
- 快速模式模板调整
- 阶段交接字段对齐

## 12.4 index
例如：

- 新任务识别维度
- 新装配规则
- 新模式判断逻辑

# 13. 使用原则

1. index 只做路由，不代替功能文档
2. spec 不写 how-to，不写施工步骤
3. design 不复述 spec，不写流水账
4. tasks 不写需求说明，只负责施工编排
5. archive 不记录废弃方案作为最终结论
6. enhancement / refactor 必须显式引用历史资产
7. 若历史资产与 Git 代码冲突，以 Git 代码为准
8. 若任务形成通用增量，需回写 rules / context / templates / index
9. 模板保持公共骨架，项目知识通过映射层进入，不应反向污染模板主骨架

---

# 14. 最终目标

本索引服务的不是“生成几个 Markdown 文件”，而是支撑 UAW 项目的完整链路：

`proposal → index 装配 → spec → design → tasks → implementation → review → archive → 下一轮 enhancement / refactor`
