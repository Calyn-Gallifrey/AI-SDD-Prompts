# 功能提案入口模板

> 本模板是任务唯一正式入口。  
> 目标：让开发人员以最低填写成本，准确启动完整链路：

`proposal → index → spec → design → tasks → implementation → review → archive`

> 设计原则：

1. 开发填写项最少，但信息必须足够
2. 固定内容后置，开发无需修改
3. 必填项靠前，按优先级排序
4. AI 读取后可精准驱动 `1.index.md`
5. 保持与 spec / design / tasks / archive 精确对应

# 8. 历史资产读取规则（固定｜无需修改）

若为 enhancement / refactor，按顺序读取：

1. `archive.md`
2. `spec.md`
3. `design.md`
4. 当前 Git 代码
5. `tasks.md`（按需）

原则：

- 先读 `archive.md`，快速了解上次最终方案、边界、决策与风险
- 再按需展开 `spec.md`、`design.md`
- `tasks.md` 仅在需要复用实施顺序 / 检查清单时读取
- Git 代码是实物基线，历史文件是知识基线。如历史资产与当前 Git 代码冲突，以当前 Git 代码为准，并在新 spec 中标明差异

# 9. 归档要求（固定｜无需修改）

## 归档文件路径

默认：

`.project-features/<sprint>/<feature-name>/archive.md`

## 归档前置条件

仅在以下条件全部满足后才允许归档：

1. `spec.md` 已确认
2. `design.md` 已确认
3. `tasks.md` 已确认
4. 代码实施已完成
5. Code Review Findings、Review-driven Auto-fix、Unit Test Summary 已输出
6. 人工最终审核已通过

## 归档标准要求

归档文件必须满足：

1. 基于最终确认版本，不记录中途废弃方案作为最终结论
2. 与当前最终 Git 代码结果一致；若存在差异，必须明确标注
3. 能支持下一次 enhancement / refactor 在不回看完整对话的情况下继续工作，快速理解本次任务的：
   - 目标
   - 边界
   - 最终方案
   - 关键决策
   - 风险
   - 推荐阅读顺序
4. 归档不得只写结论，必须保留必要的决策依据与取舍说明
5. 不堆砌执行流水账，只保留后续复用所需信息
6. 若本次任务形成新的通用规则、索引增量或模板修正，必须在归档中明确记录
7. 若本次任务未完全完成，必须在归档中明确标注“未完成项 / 遗留风险 / 后续建议”，不得伪装为完整闭环
8. 归档完成后，应可作为下一次增强提案的优先输入资产

# 10. AI 执行流程（固定｜无需修改）

1. 读取 `1.index.md`
2. 装配 context / rules / templates
3. 扫描当前代码现状
4. 读取设计文档（如有；未指定则按 index 规则自动选择）
5. 生成 `spec.md`
6. spec 人工确认后生成 `design.md`
7. design 人工确认后生成 `tasks.md`
8. 按 `spec.md + design.md + tasks.md` 实施代码
9. 输出：
   - 变更文件清单
   - 变更摘要
   - Code Review Findings（内部评审结果，不生成 HTML 报告）
   - Review-driven Auto-fix 结果
   - Unit Test Summary
   - 已知问题 / 风险点
10. 人工审核实施结果；如未通过，需基于当前任务上下文继续修正，不得直接跳过审查进入归档
11. 仅在以下条件全部满足后，才允许执行归档：
- `spec.md` 已确认
- `design.md` 已确认
- `tasks.md` 已确认
- 代码实施已完成
- Code Review Findings、Review-driven Auto-fix、Unit Test Summary 已输出
- 人工最终审核已通过
12. 执行归档时，需按归档标准生成 `archive.md`，不得仅生成空壳文件或简略结论
13. 如本次任务产生通用规则增量，需同步更新 `.project-ai/context/1.index.md` 或对应 rules / templates
14. 若本次任务后续可能继续 enhancement / refactor，需在 `archive.md` 中明确写出下一次任务的推荐阅读顺序

# 13. 优先级说明（固定｜无需修改）

- P0：紧急任务，如生产问题、上线阻塞、客户测试阻塞；可优先处理，并允许按 `Fast Lane` 快速流程推进。
- P1：当前 Sprint 正常需求，按标准流程执行。
- P2：优化项、技术债、可延期需求，排期处理，可降低处理优先顺序。

填写原则：按业务影响与时间要求判断；无法判断时默认 P1。所有任务都填 P0，这字段就废了。

# 15. SDD Code Review 接入说明（固定｜无需修改）

本功能任务在 `tasks.md` 确认并完成代码实现后，必须启动 SDD 内部代码评审入口：

```text
Entry Mode: SDD_TASK_CODE_REVIEW
Feature Directory: .project-features/<SprintN>/<feature-name>/
SDD Artifacts:
- ./proposal-input.md
- ./spec.md
- ./design.md
- ./tasks.md
```

SDD 内部 Code Review 是流程质量闸门，不是报告生成任务。

规则：

1. 不生成 HTML 代码评审报告。
2. 不读取 `代码评审统计报告模板_总.html` 和 `个人代码评审报告模板.html`。
3. 不创建 `reports/code-review/YYYY-MM-DD/` 目录。
4. 必须输出 Code Review Findings。
5. 发现 P0/P1 问题后必须直接进入 Review-driven Auto-fix。
6. Auto-fix 完成后必须进入 Unit Test Generation / Unit Test Summary。
7. Code Review Findings、Auto-fix Summary、Unit Test Summary 完成之前，禁止生成 `archive.md`。

独立 Git 范围代码评审请使用 `Entry Mode: STANDALONE_GIT_RANGE_REVIEW`，该模式不属于 SDD 功能任务链路。
