## 3. 執行前檢查
在開始前先確認：
1. 是否明確本次是新增 / 增強 / 重構 / 修復
2. 是否已明確存量與增量邊界
3. 是否已拿到正確的 package 路徑
4. 是否已定位相關存量代碼
5. 是否已明確需讀取的 rules / context / templates

---

## 4. 任務步驟

### 步驟 1：讀取 spec 與 design
- 提取本次功能目標、邊界、驗收標準、設計落位
- 列出需新增 / 修改的文件清單

### 步驟 2：讀取存量代碼
- 掃描相關 controller / service / mapper / entity / dto / helper / enum / xml
- 確認當前 Git 代碼基線與 spec / design 是否一致

### 步驟 3：生成 / 修改對象類
- 參考：BO / DTO / VO / Entity 規則
- 輸出：對象類文件

### 步驟 4：生成 / 修改業務代碼
- 參考：後端 API 規則、當前用戶規則、MapStruct 規則
- 輸出：controller / service / converter / helper 等代碼

### 步驟 5：生成 / 修改 ORM 代碼
- 參考：MyBatis ORM 規則
- 輸出：mapper / xml / dto / result 類

### 步驟 6：生成 / 修改外部集成代碼（如適用）
- 參考：EPI / OM 對接規則
- 輸出：ACL / helper / parser / remote 調用邏輯

### 步驟 7：補充測試
- 參考：testing 規則
- 輸出：unit test / controller test / strategy test

### 步驟 8：自檢與優化
至少檢查：
- 包路徑是否正確
- 對象命名是否符合規範
- current user 是否放在正確層
- MapStruct / converter 是否符合規則
- ORM namespace / xml 路徑 / where / foreach 是否正確
- 驗收標準是否被覆蓋

### 步驟 9：輸出變更摘要
輸出：
- 新增文件
- 修改文件
- 風險點
- 未完成項

### 步驟 10：生成 commit message
- 參考：`templates/3.根据本次变更内容生成git_commit记录.md`
- 輸出：建議提交信息
