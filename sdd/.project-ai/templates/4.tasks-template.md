## 4. 任务分阶段执行（Phases）

### Phase 0：执行前确认
#### 目标
确认本次施工的双基线、边界和依赖已经齐备。

#### 输入
- spec
- design
- 当前代码扫描结果

#### 执行动作
- 确认功能目标与边界
- 确认包路径与落位
- 确认不可变区域
- 确认必须复用的存量类 / helper / mapper / path
- 确认测试要求

#### 输出物
- 执行前确认结论
- 风险提示
- 依赖清单

#### Dependencies
- spec 已确认
- design 已确认

---

### Phase 1：对象与结构落位
#### 目标
完成 BO / DTO / VO / Entity / Enum / 常量等对象与结构的新增或调整。

#### 输入
- spec
- design
- model rules

#### 执行动作
- 新增或调整 BO / DTO / VO / Entity
- 落位 package
- 补充 enum / 常量
- 校验对象命名与路径

#### 输出物
- 新增 / 修改对象文件清单
- 包落位结果

#### Dependencies
- Phase 0 完成

---

### Phase 2：核心实现
#### 目标
完成 controller / service / mapper / xml / converter / 外部调用等核心实现。

#### 输入
- spec
- design
- backend / ORM / mapstruct / current user / integration rules

#### 执行动作
- 实现 controller
- 实现 service
- 实现 mapper / xml
- 实现 converter / helper / 依赖调用
- 保持边界约束不被破坏

#### 输出物
- 核心实现文件清单
- 变更摘要

#### Dependencies
- Phase 1 完成

---

### Phase 3：测试与校验
#### 目标
补齐最小必要测试并完成规则校验。

#### 输入
- testing rules
- spec 验收标准
- design 测试设计考量

#### 执行动作
- 补 service 单测
- 补 controller 单测
- 按需补 converter / static / strategy 测试
- 检查空结果 / 边界 / 异常场景

#### 输出物
- 测试文件清单
- 测试执行结果

#### Dependencies
- Phase 2 完成

---

### Phase 4：实施后自检
#### 目标
在人工审核前，形成完整可审查输出。

#### 输入
- 所有实现结果
- 测试结果
- spec / design / tasks

#### 执行动作
- 检查规则遵循情况
- 检查文件路径与命名
- 检查不可变边界是否被破坏
- 检查当前实现与 spec / design 是否一致
- 汇总已知问题与风险

#### 输出物
- 变更文件清单
- 变更摘要
- 编译结果
- 测试结果
- 已知问题 / 风险点

#### Dependencies
- Phase 3 完成

---

## 5. 明确执行顺序
本次任务必须按以下顺序执行，不得跳步：

1. Phase 0：执行前确认
2. Phase 1：对象与结构落位
3. Phase 2：核心实现
4. Phase 3：测试与校验
5. Phase 4：实施后自检
6. 人工审核
7. 如审核不通过，回到对应 Phase 修正
8. 审核通过后，进入 archive

---

## 6. 依赖关系（Dependencies）
### 6.1 上游依赖
- spec 已确认
- design 已确认
- 相关 rules 已装配
- 当前代码扫描结果已生成

### 6.2 施工依赖
- 包路径明确
- 外部依赖明确
- 不可变边界明确
- 测试范围明确

### 6.3 下游依赖
- 实施结果需提供给人工审核
- 审核通过后才允许归档
- 若有规则增量，需回写 `.project-ai`

---

## 7. 实施后自检要求
在人工审核前，必须完成以下自检：

- 是否遵循已装配 rules
- 是否与 spec 目标一致
- 是否与 design 设计一致
- 是否修改了禁止变更区域
- 是否补齐必要测试
- 是否输出完整变更摘要
- 是否标明已知问题与风险
- 是否具备归档前置条件

---

## 8. 人工审核前输出要求
提交给人工审核前，必须输出：

1. 变更文件清单
2. 变更摘要
3. 编译结果
4. 测试结果
5. 已知问题 / 风险点
6. 是否需要继续修正的建议

---

## 9. 交付物清单
本次 tasks 执行完成后，至少应交付：

- `spec.md`
- `design.md`
- `tasks.md`
- 已修改 / 新增代码
- 测试代码
- 实施后自检结果
- 提交人工审核的输出摘要
- 审核通过后生成的 `archive.md`

---

## 10. 归档前置条件
只有满足以下条件，才允许进入 archive：

1. `spec.md` 已确认
2. `design.md` 已确认
3. `tasks.md` 已确认
4. 代码实施已完成
5. 编译 / 测试结果已输出
6. 人工最终审核已通过
7. 已形成变更文件清单与实施摘要
8. 已知问题 / 风险点已明确记录

---

## 11. 与 `archive-template.md` 的衔接
在满足归档前置条件后，tasks 的执行结果必须能直接供 `archive-template.md` 使用，包括：

- 本次最终采用的 spec / design / tasks 路径
- 最终实施结果摘要
- 变更文件清单
- 关键决策与取舍
- 编译 / 测试结果
- 遗留事项与后续建议
- 是否回写 rules / index / templates
